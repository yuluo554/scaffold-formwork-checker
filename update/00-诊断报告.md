## 二、缺陷清单（D1–D9）

### D1（P0）Python 3.8 已停止安全支持，但仓库 floor 与 CI、以及发布的 exe 都还基于 3.8

- `pyproject.toml`：`requires-python = ">=3.8"`
- `classifiers`：`Programming Language :: Python :: 3.8` 与 `:: 3.12` 并列
- `CI`：矩阵 `python-version: ["3.8", "3.12"]`
- 发布附件 `sfc-v1.0.0-windows-x64-onedir.zip` 是 **Python 3.8.8** 打的（本机 venv 实测同版本）
- Python 3.8 的生命周期已于 **2024-10-07** 结束（`endoflife.date` 的 API 在本机被证书问题挡住，
  未能直连核实；**执行方请用官方源复核一次**）。
  但**不需要靠这条**也能判定问题 —— 见 D2，依赖锁定的证据是本地可直接验证的。

### D2（P0）3.8 这一个约束卡住 5 个依赖的升级（PyPI 实测 requires_python）

| 依赖 | 仓库声明 | 本地实装 | 最新版 | 最新版 requires_python | 结论 |
|---|---|---|---|---|---|
| PySide6 | `>=6.6,<6.7` | 6.6.3.1 | **6.12.0** | `>=3.10` | 落后 **6 个小版本**，纯因 3.8 |
| pyinstaller | `>=5.13,<6` | 5.13.2 | **6.22.3** | `>=3.8` | 6.x 在 py3.8 上崩（仓库 plan/06 #27 实录） |
| pytest | `>=7` | 8.3.5 | **9.1.1** | `>=3.10` | 因 3.8 卡住 |
| python-docx | `>=0.8.11` | — | **1.2.0** | `>=3.9` | 因 3.8 卡住 |
| pypdf | `>=3` | 5.9.0 | **6.21.1** | `>=3.9` | 因 3.8 卡住 |

命令：`pypi.org/pypi/<pkg>/json` 读 `info.requires_python`（PyPI JSON API 直读）。

**仓库自己知道这件事**：`plan/06` 决策 #27 明确写「PySide6 锁 6.6.3.1（py3.8 支持最后线，
6.7+ 元数据 requires-python>=3.9；extras 写上限防干净环境解析到破坏版本）」。

> 也就是说：**当初的上限不是设计选择，是被 3.8 逼的**。抬 floor 之后这些上限应当重新评估。

### D3（P0，与 D1/D2 同源）代码本身其实不依赖 3.8 的任何特性

实测：`src/` 里**没有** `match` 语句、没有海象 `:=`；3.9+ 的类型写法用的是**字符串注解**规避：

```
src/.../cli.py:99   def _optional_deps_status() -> "list[str]":
src/.../cli.py:120  def _find_data_dir() -> "str | None":
```

所以「抬 floor」的代价主要在**依赖与发布**，不在改代码（`src/` 5846 行无需为 3.9/3.10 重写）。
这一点让批次 1 的工作量比看起来小 —— 但仍需实测（见路线）。

### D4（P1）条款库有「核对过」但没有「何时复核」——规则引擎的持续正确性缺口

实测 `data/knowledge/clauses/` 的 7 个文件：

| 文件 | 条目数 | status | fetched |
|---|---|---|---|
| `jgj130_clauses.json` | 44 | 已核对 44 | **全为 None** |
| `jgj162_clauses.json` | 15 | 已核对 15 | **全为 None** |
| `decree37_clauses.json` | 7 | 已核对 7 | **全为 None** |
| `notice31_clauses.json` | 8 | 已核对 8 | **全为 None** |
| `formulas.json` | 22 | **已核对 21 + 待核对 1**（`F-J162-sidepressure`） | — |
| `thresholds.json` | 36 | 已核对 36 | — |
| `panorama.json` | 9 条目 | 条目级 `status` 全为 None（**核对状态在 `basis[]` 层**，均为「已核对」） | — |

grep 结果：`next_check` / `review` / `expire` / `到期` / `生效日期` 在条款库 JSON 里 **0 命中**。

**含义**：引用的规范是 `JGJ 130-2011` / `JGJ 162-2008` / 住建部令第37号 / 建办质〔2018〕31号，
最新一份是 2018 年的。工具现在无法回答「我依据的这份还是现行版吗」——
对「结论要挂条款号」的规则引擎，这是**比代码 bug 更值得处理的一类风险**。
（注意：这**不是说规范一定被替代了** —— 需要核实，见路线批次 3。）

### D5（P1）1 条公式处于「待核对」

`formulas.json` 22 条里 21 条已核对，`F-J162-sidepressure` 仍为待核对。
`data/README.md` 说明它「首期模块不依赖」，所以不是当前红项，但它是条款库里**唯一非绿的状态位**。

### D6（P1）无 `CHANGELOG.md`

`ls CHANGELOG*` → 不存在。版本历史分散在 `plan/RELEASE-M6.md` 与 commit message 里，
对外部用户没有可读的变更记录载体。

### D7（P1）README 在「产品页」标尺下不合格（FAIL 3 / WARN 3）

用运维计划的阶段二标尺 `check_readme_gate.py --strict` 实测：

```
FAIL  安装命令在第 36 行（阈值 30）——向下移动正文，把它提上来
FAIL  前 30 行出现里程碑/DoD（移到 DEVELOPMENT.md）
FAIL  没有「判定依据」表（版本 + 生效日期）
WARN  第 1 行标题未含定位（建议 `名字 — 一句话`）
WARN  README 177 行（建议 ≤ 120，超出部分拆到 DEVELOPMENT.md）

```

**这条特别值得注意**：这个仓库明明**已经拥有**最硬的判定依据素材
（44+15+7+8 条已核对条款、36 条阈值、逐条 `clause_ref` 锚点），
却**没有在 README 上呈现成「判定依据表（版本 + 生效日）」** —— 这是「有资产、没展示」。

### D8（P2）`panorama.json` 条目级缺 `status`

9 个危大条目的 `status` 均为 `None`，核对状态只存在于 `basis[]` 子对象里。
`data/README.md` 写「已核对（basis 全部已核对）」——语义上一致，但**机器无法在条目级判定**，
任何「扫描条款库找未核对项」的守门脚本都会漏过它（对比：其他 4 个条款库文件都有条目级 `status`）。

### D9（P2）本机占用与发布纪律（记录，非缺陷）

- 本机 `.venv` 521MB / `dist` 176MB / `build` 21MB / `output` 2.9MB —— **均在 `.gitignore` 内**，无提交风险
- `data/knowledge/raw/`（规范原文全文）**不入仓**（版权红线，`.gitignore` 已挡）—— 这是正确的取舍，
  但也意味着**第三方无法仅凭仓库复核条文原文**，只能依赖 `data/README.md` 的 sha256 台账。
  重发版时注意别把这个目录带进 exe（现有 `tools/build_exe.py --check` 已有禁区扫描，实测存在）

## 三、做得好的部分（迭代中不要破坏）

- **314 个测试 + 三套 benchmark 全绿**，且 CI 是**四矩阵**（ubuntu/windows × 3.8/3.12）——
  跨平台跨版本真跑，不是单机自证。
- **零核心依赖**（`dependencies = []`）：引擎是确定性纯 Python，这对「验算结论可复现」是根本性优势。
- **条文纪律落成了机制**：`status=待核对` 的条款/公式**不得进入计算路径**，而且这句话是有代码与测试兜着的（不是 README 上的口号）。
- **冻结数据有生成器**：`tools/gen_examples.py`（复算断言）、`tools/gen_synthetic.py`（固定 seed）、
  `tools/build_exe.py --check`（构建后禁区扫描 + sha256 对账）——数据不是手抄的。
- **CI 首跑抓出真 bug 并修**：`create_system` 随平台漂移导致 docx 冻结比对失败 →
  生成器改为 `ZIP_STORED` + 固定 `create_system`/`external_attr`（决策 #33），
  这类「在别的平台才暴露」的问题能被 CI 抓住，说明冻结纪律是真在执行。
- **决策记录完整**：`plan/06` 34 条决策带日期、理由、状态，且有一条「决策变更记录」预留位。

## 四、本次迭代的目标（建议）

一句话：**让这个工具脱离 EOL 解释器，并把「条款库会过期」这件事变成机制。**

三条理由：
1. 交付物（52MB exe）是用一个已停止安全支持的 Python 打的 —— 在施工安全领域这不好解释；
2. 5 个依赖被 3.8 锁在旧线（PySide6 落后 6 个小版本），抬 floor 后这些上限该重新评估；
3. 规则引擎的**持续正确性**没有任何机制保障（D4），而这恰好是很容易补、且一旦补上就长期有效的东西。

详见 `01-迭代路线.md`。
