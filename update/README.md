## 一句话结论

**这个仓库的技术债不在代码，在「解释器版本」**：`requires-python >=3.8` + CI 3.8 矩阵 +
发布的 exe 基于 Python 3.8，而 **Python 3.8 已于 2024-10-07 停止安全支持**。
更关键的是：**3.8 这一个约束卡住了 5 个依赖的升级**（实测 PyPI 的 `requires_python`）：

| 依赖 | 仓库现值 | 最新版 | 最新版要求 | 被 3.8 卡住？ |
|---|---|---|---|---|
| PySide6 | `>=6.6,<6.7`（实装 6.6.3.1） | **6.12.0** | `>=3.10` | ✅ 卡住（落后 6 个小版本） |
| pyinstaller | `>=5.13,<6`（实装 5.13.2） | **6.22.3** | `>=3.8` | ⚠️ 部分（6.x 在 py3.8 上崩，是 3.8 专属问题） |
| pytest | `>=7`（实装 8.3.5） | **9.1.1** | `>=3.10` | ✅ 卡住 |
| python-docx | `>=0.8.11` | **1.2.0** | `>=3.9` | ✅ 卡住 |
| pypdf | `>=3`（实装 5.9.0） | **6.21.1** | `>=3.9` | ✅ 卡住 |

> 仓库自己的 `plan/06` 决策 #27 就写着「PySide6 6.7+ 元数据 requires-python>=3.9」——
> 也就是说**当初就是被 3.8 逼着上锁的**，这一点仓库自己记录得很清楚。

## 需要用户拍板的一项

**要不要放弃 Python 3.8？** 这是本次迭代的**唯一分叉点**，两条路后果不同：

| 方案 | 收益 | 代价 |
|---|---|---|
| **A. 抬到 `>=3.10`**（推荐） | 解锁 PySide6 6.12 / pyinstaller 6.x / pytest 9 / docx 1.2 / pypdf 6；exe 脱离 EOL 解释器 | **对 pip 用户是破坏性变更** → 需发 2.0.0；Win7/老环境用户可能受影响 |
| **B. 只抬到 `>=3.9`** | 解锁 docx 1.2 / pypdf 6；PySide6 可到 6.9 线 | PySide6 6.10+/pytest 9 仍不可用 |
| C. 保持 3.8 | 无破坏 | 继续用 EOL 解释器 + 5 个依赖停在旧线；**exe 也是 3.8 打的** |

> 我的建议是 A，理由：这个工具的主要交付形态是 **Windows 免安装 exe**（v1.0.0 的 Release 附件
> 52,146,144 字节），pip 用户占比很小；而「用 EOL 解释器打出来的安全验算工具」在施工安全场景里
> 是个说不清的问题。但这是**你的决定**，不是执行方能自行选的。
